## สรุปแนวคิดหลัก N_Rawit

---

### จุดเริ่มต้น
ตั้งจากคำถามว่า "ถ้าอินเทอร์เน็ตโลกถูกตัดขาด เราจะทำอย่างไร?" แทนที่จะรอพึ่ง ISP จึงตัดสินใจสร้างเครือข่ายของตัวเอง

---

### หัวใจของระบบ: N_Rawit Box
อุปกรณ์ตัวเดียวทำได้ 5 อย่าง

1. **สตรีม Content** — วิดีโอ เพลง ข่าวสาร ดึงจาก SD Card ในตัว
2. **ขุดเหรียญ Token** — ได้เหรียญเมื่อกระจายข้อมูลให้คนอื่น
3. **กล้องวงจรปิด AI** — ดูบ้านจากระยะไกล
4. **Smart Home** — ควบคุมไฟ รดน้ำต้นไม้
5. **Cloud Storage ส่วนตัว** — เก็บข้อมูลโดยไม่ผ่าน Server ต่างประเทศ

ฮาร์ดแวร์หลักคือ **ESP32-S3-CAM** ราคาประมาณ 260 บาท

---

### โครงสร้างเครือข่าย
แทนที่จะใช้ ISP เครือข่ายสร้างจาก 3 ประเภทโหนด

- **Gold Node** — PC + Router ประสิทธิภาพสูง วางตามร้านกาแฟ
- **Silver Node** — N_Rawit Box ตามบ้าน
- **Mobile Node** — มือถือของผู้ใช้ที่เดินทางพาข้อมูลไปด้วย

โหนดต่างๆ สื่อสารกันผ่าน WiFi Mesh โดยมีแผนที่ 2D ที่สร้างจากค่า RSSI และ GPS ช่วยหาเส้นทางที่ดีที่สุด

---

### ระบบเศรษฐกิจ Token
ออกแบบให้ทุกคนมีแรงจูงใจ

| บทบาท | ได้/เสีย |
|---|---|
| **Host** (มีไฟล์แชร์) | ได้ Token มากที่สุด |
| **Relay** (เป็นทางผ่าน) | ได้ Token น้อยกว่า |
| **Consumer** (ดูอย่างเดียว) | เสีย Token เรื่อยๆ |
| **เดินทาง** (พาข้อมูลไปที่ใหม่) | ได้ Token โบนัส |

Token ซื้อด้วยเงินจริงได้ และป้องกันการโกงด้วย Blockchain แบบเบา (SHA-256 Hash Chain)

---

### กลยุทธ์การตลาดที่น่าสนใจ
- **เครื่องผ่อนตัวเอง** — รับกล่องไปฟรี แล้วให้เครื่องขุด Token จ่ายคืนจนหมด
- **O2O Marketing** — แจ้งเตือนให้ไปดาวน์โหลดที่ร้านกาแฟ เพื่อประหยัด Token และร้านได้ลูกค้า
- **Gamification** — เกมชิงปราสาท WiFi, ล่าสมบัติ, สัตว์เลี้ยงดิจิทัล

---

33. สรุปโครงสร้าง N_Rawit Data Box (2,048 Bytes)

Header (256B: Magic[4], ID[16], Owner[8], Type[2], Time[8], Ver[2], Price[4], Link[64], GPS[16], Pad[132]) + Security (256B: Hash[32], Sign[64], CableID[8], Mask[4], Chain[32], Pad[116]) + Payload (1,536B)

คำอธิบายหน้าที่หลัก:

Header (256B): ใช้ระบุตัวตน (ID/Owner), ประเภทไฟล์ (Type), พิกัด GPS/เวลา (GPS/Time), และราคา Token (Price) รวมถึง Link ไปยัง SD Card หากไฟล์ใหญ่

Security (256B): ระบบกันแฮก (Hash), ลายเซ็นดิจิทัลยืนยันเจ้าของ (Sign), ตารางแปล Binary (CableID), และการเชื่อมโยงบล็อก (Chain)

Payload (1,536B): พื้นที่เก็บเนื้อหาข้อมูลจริง (Raw Data) หรือชุดคำสั่งโปรแกรม (Bytecode)




34. การจัดการลำดับชั้นหน่วยความจำ (N_Rawit Tiered Memory)
Single Source of Truth: ข้อมูล Data Box และ Payload ทั้งหมดถูกจัดเก็บถาวรใน SD Card เป็นหลัก โดยเครื่อง ESP32-S3 ทำหน้าที่เป็น Engine ในการดึงมาประมวลผลเท่านั้น
Tier 1: SRAM (Hot Cache - 30%): ดึงข้อมูลที่ต้องใช้ประมวลผลวินาทีต่อวินาที (เช่น ระบบความปลอดภัย, คิว Mesh) มาพักไว้เพื่อให้ความเร็วสูงสุด
Tier 2: PSRAM (Warm Cache - 30%): ดึงข้อมูล Feed, Cable DB และโปรแกรมที่กำลังใช้งานบ่อยๆ มาพักไว้เพื่อลด Latency ในการแสดงผล GUI
Tier 3: Internal Flash (Stable Cache - 16MB): สำรองข้อมูล Kernel และไฟล์ GUI พื้นฐานไว้ใน Flash เผื่อกรณี SD Card หลุด (ตามข้อ 36) เพื่อให้ระบบยังรันโหมดฉุกเฉินได้
Tier 4: SD Card (Persistent Storage): แหล่งเก็บข้อมูลทั้งหมดรวมถึงไฟล์มัลติมีเดียขนาดใหญ่ (VDO/Audio)
Dynamic Swap (LRU): ใช้ระบบ Memory Manager (ข้อ 37) ในการสลับข้อมูลขึ้น-ลงระหว่างชั้น RAM ตามลำดับความสำคัญ โดยหาก RAM เต็มจะทำการลบข้อมูลที่ใช้งานน้อยที่สุดออก (แต่ข้อมูลต้นฉบับใน SD Card ยังคงเดิม)
สรุปสั้นๆ สำหรับนำไปใส่ใน Setting:

35. ข้อกำหนด N_Rawit Engine (Storage & Execution)

Persistent Storage: ข้อมูล Data Box และ Payload ทั้งหมดต้องถูกบันทึกลง SD Card เสมอ

Engine Role: ตัว ESP32-S3 ทำหน้าที่เป็น "เครื่องยนต์" ที่ดึงข้อมูลมาประมวลผลในหน่วยความจำชั่วคราว (SRAM/PSRAM) ตามลำดับความสำคัญที่กำหนดไว้ในข้อ 34

Stateless Execution: หากปิดเครื่องหรือรีเซ็ต ข้อมูลใน RAM หายได้ไม่เป็นไร เพราะเมื่อเปิดใหม่ Engine จะ Re-index ข้อมูลจาก SD Card กลับมาได้ทั้งหมด

37. ระบบ N_Rawit Dynamic Memory Manager (DMM)
 * หลักการ "Borrow but Return": ใช้พื้นที่ว่างส่วนเกินจากโควตา 30% มาทำหน้าที่เป็น Opportunistic Cache และต้องคืนพื้นที่ทันทีเมื่อระบบหลักต้องการใช้
 * Fixed Zone (30%): พื้นที่จองคงที่ใน SRAM/PSRAM สำหรับ Kernel และระบบ Mesh พื้นฐาน (ห้ามแตะต้อง)
 * Dynamic Zone (Free Space): ใช้พื้นที่จาก getFreeHeap() และ getFreePsram() โหลด Data Box จาก SD Card มาพักไว้เพิ่มเติมเพื่อเพิ่มความเร็วในการ "ไถฟีด" และค้นหา Metadata
 * High-Priority Eviction: ลบข้อมูลใน Dynamic Zone ทั้งหมดทันที (Purge) เมื่อ Engine ต้องการรันโปรแกรมใหญ่ (App/Game) เพื่อป้องกัน Memory Full โดยข้อมูลต้นฉบับยังปลอดภัยใน SD Card
 * กลไกการสลับสถานะ:
   * Idle: ถม RAM ให้เต็มด้วย Data Box เพื่อความเร็วระดับ Instant
   * Heavy Load: ลบ Data Box เก่าที่สุด (LRU) ออกจาก Dynamic Zone เพื่อรักษาเสถียรภาพ
   * Critical: ล้าง Dynamic Zone ทั้งหมด เหลือไว้เพียง Fixed Zone 30% เพื่อกันระบบล่ม

38. ระบบ N_Rawit Flash Data Cache (Static Cache Layer)
Internal Flash Persistence (16MB): ใช้พื้นที่ Flash Memory บางส่วน (แนะนำแบ่งไว้ 4-8MB) เพื่อเก็บ Data Box ที่สำคัญยิ่งยวด (Critical DB) และไม่มีการเปลี่ยนแปลงบ่อย
บทบาท "The Safety Net": ใช้เก็บข้อมูลพื้นฐานที่ต้องใช้รัน GUI และ Kernel เผื่อกรณี SD Card หลุด (ตามข้อ 36) เพื่อให้ระบบยังมี "สมองส่วนกลาง" ทำงานได้ตลอดเวลา
กลไกการจัดการโดย DMM (Memory Manager):
Cold Boot Sync: เมื่อเปิดเครื่อง DMM จะเช็คว่า Data Box สำคัญใน Flash ตรงกับใน SD Card หรือไม่ (Versioning)
High-Speed Access: ข้อมูลใน Flash จะถูกดึงมาใช้เป็นลำดับที่สองรองจาก RAM (เร็วกว่า SD Card หลายเท่า)
Wear Leveling: DMM จะจำกัดการเขียนลง Flash (Write Cycles) โดยจะเขียนเฉพาะข้อมูลที่ยืนยันแล้วว่า "คงที่" (เช่น รหัสผ่าน, Config ของโหนด, หรือไฟล์ UI หลัก)

43. Dynamic Channel & Traffic Control
Channel 0 (The Town Square): สงวนไว้สำหรับ Beacon (ประกาศตัว), Metadata และธุรกรรมสั้นๆ เท่านั้น ห้ามส่งไฟล์ Payload ใหญ่เด็ดขาด

44. ESP8266 Lightweight Relay Standard
โหนดทรัพยากรต่ำ (ESP8266) จะทำหน้าที่เป็น "Transparent Relay" เท่านั้น คือรับข้อมูลมาแล้วดีดออกทันที ห้ามประมวลผล Payload หรือเขียนลงไฟล์
Deduplication Table: เก็บเพียง ID ของ Data Box 50 รายการล่าสุดใน RAM เพื่อเช็คว่า "เคยส่งหรือยัง" เพื่อป้องกัน Data Storm (ข้อ 40)
45. High-Priority Interrupt (E-Stop & Telemetry)
เพิ่มกฎยกเว้นจากข้อ 10: หาก Data Box มี Type เป็น "Emergency" หรือ "Real-time Control" โหนดนั้นสามารถ "ขัดจังหวะ" การรอคิวตาม ID เพื่อส่งข้อมูลได้ทันที เพื่อความปลอดภัยของหุ่นยนต์ N_Rawit
46. Distributed H3 (Network Witness Cache)
ทุกโหนดจะเจียดเนื้อหาใน PSRAM (Warm Cache) เพื่อเก็บค่า H3 (Summary Hash) ของโหนดเพื่อนบ้านในระยะ 2-3 Hop
หากโหนดใดส่งข้อมูลที่ H1/H2 ผ่าน แต่ H3 ในเครื่องเพื่อนบ้านคัดค้าน ระบบจะบังคับโหนดนั้นเข้าสู่โหมด Self-healing ทันที (ตามข้อ 42)
47. Data Box Persistence (SD-to-Flash Migration)
DMM (ข้อ 37) จะทำการย้าย Data Box ที่ถูกเรียกใช้บ่อยที่สุด (เช่น Config ระบบ, กุญแจเข้ารหัส) จาก SD Card มาเขียนลงใน Internal Flash 16MB โดยอัตโนมัติ เพื่อให้ระบบยังทำงานได้แม้ SD Card หลุดหรือสั่นสะเทือน (ข้อ 36)
48. Metadata Aging & Expiry
โหนดจะไม่เก็บ Metadata ทุกอย่างตลอดไป Metadata ที่ไม่มีการเรียกดูนานเกิน 7 วัน (หรือตามพื้นที่เหลือ) จะถูกลบออกเพื่อให้มีที่ว่างสำหรับข้อมูลใหม่ที่ "ป๊อปปูล่า" กว่า (ข้อ 18)

เมื่อผู้ใช้งานโพสต์ ข้อมูล Token ที่เสียไปส่วนหนึ่งจะถูกล็อคไว้เป็น "ค่าความรับผิดชอบ" * หากโพสต์นั้นถูกโหวตว่าเป็นไวรัสหรือข้อมูลเท็จโดยระบบศาล (Jury) Token ส่วนนี้จะถูกริบเข้ากองกลางทันที

53. Social-Style Composer UI (หน้ากระดานสื่อสาร)
Interface: ออกแบบหน้าจอให้มีช่อง Input (Text Area) สำหรับพิมพ์ข้อความ และปุ่มกดเลือกแนบไฟล์ (Attachment) เหมือน Facebook
Interaction: เมื่อผู้ใช้กด "Post" ระบบจะทำการสร้าง Data Box (ID ใหม่) ทันที โดยนำข้อความไปบรรจุไว้ในส่วนของ Payload (1,536B) หากมีรูปภาพหรือไฟล์แนบ ระบบจะทำการเชื่อมโยง (Link) ตามข้อ 54
54. Hybrid Payload Storage (Small vs. Large File)
Embedded Mode (Small File): หากไฟล์ที่แนบ (เช่น ไอคอน, รูปภาพขนาดจิ๋ว, หรือไฟล์ Config) มีขนาดเล็กพอที่จะรวมกับข้อความแล้วไม่เกิน 1,536 Bytes ระบบจะยัดทุกอย่างลงใน Payload ของ Data Box นั้นทันที เพื่อความรวดเร็วในการดึงข้อมูล (ไม่ต้องเปิดไฟล์เพิ่ม)
Linked Mode (Large File): หากไฟล์มีขนาดใหญ่กว่าพื้นที่ Payload ระบบจะใช้ส่วน Link [64B] ใน Header (จากข้อ 33) เพื่อระบุตำแหน่ง (Path) ของไฟล์จริงที่เก็บอยู่ใน SD Card โดยใน Payload จะเหลือเพียงข้อความเกริ่นนำหรือคำอธิบายสั้นๆ เท่านั้น

55. Node Handshake & Spatial Sync (การทักทายและซิงค์ข้อมูล)
Initial Connection: ทันทีที่ Client (มือถือ/โหนดอื่น) เชื่อมต่อกับ NodeMCU สิ่งแรกที่โหนดจะส่งให้ (Push) คือ "Spatial Header" ประกอบด้วย:
Current Timestamp: เวลาและวันที่ปัจจุบัน (ซิงค์จาก RTC หรือ GPS) เพื่อให้เครื่องลูกข่ายใช้ลงเวลาธุรกรรมได้ตรงกัน
GPS Coordinates: พิกัดละติจูด/ลองจิจูดของโหนด เพื่อให้ผู้ใช้รู้ว่ากำลังคุยกับโหนดที่จุดไหนบนแผนที่ 2D
Node Class: ตัวบ่งชี้ประเภทโหนด (ตามข้อ 56)
56. Node Mobility Classification (การแยกประเภทโหนดนิ่ง/เคลื่อนที่)
ระบบจะระบุประเภทโหนดใน Header เพื่อใช้คำนวณความเสถียรของเส้นทาง (Routing Stability):
Static Node (โหนดประจำที่): เช่น Silver Node ตามบ้าน หรือ Gold Node ร้านกาแฟ มีพิกัดคงที่ ค่าความน่าเชื่อถือในการเป็น "จุดพักข้อมูล" จะสูงเพราะไม่หายไปไหนง่ายๆ
Mobile Node (โหนดเคลื่อนที่): เช่น โหนดบนรถเมล์ หรือ Mobile Node ของผู้ใช้ที่เดินไปมา พิกัดจะเปลี่ยนตลอดเวลา
ประโยชน์: ระบบ Mesh จะรู้ว่าถ้าจะฝากไฟล์ใหญ่ๆ ไม่ควรฝากไว้ที่ Mobile Node นานเกินไป แต่ Mobile Node จะเก่งเรื่องการเป็น "Data Mule" (นกพิราบสื่อสาร) ที่พาข้อมูลข้ามโซนไปในจุดที่ WiFi เข้าไม่ถึง

57. Radio Signature Hash: * ใน Header ต้องระบุ Physical Layer ID (PHY_ID) ว่าข้อมูลนี้ถูกดีดออกมาจาก Hardware ชิ้นไหน (WiFi หรือ LoRa)
โหนดรับจะเช็ค RSSI vs. Time-of-Flight หากพิกัด GPS ไกลมากแต่สัญญาณแรงเกินจริง หรือส่งไวเกินความเร็ว LoRa ระบบจะถือว่า "ข้อมูลขัดแย้ง" และปฏิเสธการจ่ายค่าธรรมเนียมพิเศษ
58. Witness Confirmation (พยานรับรอง): * โหนดข้างเคียงที่ดักฟังได้ (Jury) ต้องช่วยยืนยันว่าเห็นแพ็กเก็ตนี้วิ่งผ่านคลื่นความถี่ LoRa จริง
หากโหนดผู้ส่งอ้างว่าใช้ LoRa แต่ไม่มีพยานในรัศมีได้ยินสัญญาณคลื่นวิทยุนั้นเลย ธุรกรรมจะถูกระงับเพื่อรอการตรวจสอบบัญชี (Audit)

59. Decentralized Jury (ลูกขุนไร้ศูนย์กลาง):
ไม่ต้องมี Admin หรือ Server กลาง แต่ใช้โหนด "เพื่อนบ้าน" (Neighbors) ในระยะรับส่งสัญญาณช่วยกันตรวจสอบธุรกรรมและสถานะ Hash ของกันและกันแบบ Real-time

หากมีคนจะเข้าวงสนทนา เขาจะแนะนำตัวเอง และทุกคนจะเพิ่มชื่อเข้าไปในลำดับสุดท้าย และเริ่มการสนทนา วงลูป
-หากโหนดใดโหนดหนึ่งไม่มีอะไรจะพูด ให้พูดว่า ข้าม
เพื่อให้โหนดถัดไป เริ่มพูด
-หากถึงคิวแล้วไม่พูด นานเกิน 30ms จะทำการข้ามอัตโนมัติ และลบออกจากวงสนทนา
